## 方案与决策（待产品 review 的建议）

### 用户操作

1. 在 Shadow AI 分析区增加紧凑入口：未标记时“标记 Badcase”，已有对应 Badcase 时“编辑原因”。展示状态、最近标注人和时间。旧快照的标记应明确为历史样本，不能使新输出看起来已被评过。
2. 点击只读取并打开编辑面板，不提前创建 Eval 样本或审核记录。面板显示 Ticket、反馈输出来源、冻结输出预览、快照版本及分析时间；历史数据缺失时显示未记录。
3. 失败标签多选，复用六类标签：意图错误、事实错误、缺少证据、风险遗漏、行动错误、回答不可用。
4. “Badcase 原因”填写具体错在哪里。建议新入口必填，去除首尾空格后 1–4000 字；例如“原讨论明确是 UK，方案使用 EU 路径，导致无法操作”。不要求用户推断模型或系统根因。人工标准意图、期望结果作为选填项。
5. 点击“保存 Badcase”，成功后关闭面板并更新状态、人、时间；再次打开回填标签和原因。已有 badcase 只编辑标注内容；已有 draft/eval 转为 badcase 必须经此次明确保存。
6. 本入口只承担标记与编辑原因。恢复为 Eval/Draft 可沿用主站编辑器；暂不增加自动修复、训练或知识写入流程。

### 数据与实现边界

- 继续使用现有 Eval 样本和审核记录；原因复用 notes，不新增同义的原因字段。编辑既有样本时完整保留未编辑的 manualIntent、expectedOutcome 等标注，避免局部表单使其变空。
- 第一版建议覆盖 Ticket 已有分析的反馈。首次创建时需要把实际供用户评判的 Shadow 输出、来源及分析时间冻结到现有 aiOutput JSON 中，与正式输出区分，并提供相应展示。不能把页面上的 Shadow 分析当作已冻结的正式输出。样本创建后保持冻结；发现同一快照下 AI 已重跑，明确展示原样本供用户确认，不能覆盖冻结输出或冒充本次新结果。
- Wiki 问答每次运行有自己的结果；现有样本唯一键只有 Ticket/快照，没有 Wiki run 维度。建议首版将按钮放在 Shadow 区域，Wiki 单次回答反馈需另行确认范围与运行绑定设计。人工回复草稿也不能混作模型原始输出。
- 主站已有公开接口为 `GET /api/web/lark-ticket-eval-samples`、`POST /api/web/lark-tickets/:recordId/eval-sample`、`PUT /api/web/lark-ticket-eval-samples/:sampleId`，已核对路由注册与入口测试。**以下为需要开发的扩展，不是现有能力**：按 Ticket/指定快照读取编辑上下文；创建请求携带初始 Badcase 标注并原子保存；保存携带所见输出的版本标识；更新携带 expectedUpdatedAt 并拒绝过期表单。
- 编辑上下文应由 server 生成并绑定 Ticket 三元组、thread 快照、输出来源/内容版本；首次保存前重验上下文，输出已变化返回冲突并要求重新查看。现有样本更新使用 sampleId 和 expectedUpdatedAt；检查顺序先处理已成功的 actionRunId 重试，再处理版本冲突。同一保存尝试的网络重试复用 actionRunId，新一轮编辑使用新 ID。
- 未建样本时一次事务提交样本、原因、标签及审核记录，最终状态直接为 badcase；不采用浏览器“先创建 Eval，再改 Badcase”的两次写入。已建样本时一次事务更新标注和审核记录。两个客户端同时首次保存时，仅一个成功，另一方收到冲突，不能把已有样本当作其保存已成功。
- 新入口要求原因的校验放在其对应的 Zod 请求分支；通用 Eval 当前允许空备注的契约不默默收紧。若希望所有入口都要求原因，实施前确认并同步主站校验、DTO 和验收。旧数据可读，不补造原因。
- 并发保护要覆盖同一数据的主站编辑入口：主站提交 expectedUpdatedAt，服务端原子比较。否则只能防住 Lark 与 Lark 的并发，不能宣称跨入口防覆盖。历史客户端缺少版本字段的兼容/拒绝策略需随实施明确。
- 身份与时间由 Web Session/服务端确定；输入不能指定标注人。新增读取及写入应核对用户 platformLists 权限及目标 Ticket 可访问范围。新流程携带 actionRunId，错误保留 layer/module/stage/errorCode，日志只记安全摘要。
- 原因以纯文本展示。成功以业务响应及重新读取为依据；保存失败保留草稿并可重试，取消不写入。切换 Ticket 要隔离迟到的读取/保存响应。

### 需要产品确认的语义

| 项目 | 本草案建议 | 另一种范围的影响 |
| --- | --- | --- |
| “更新原因” | 编辑当前 Badcase 的问题说明，复用 notes | 若每次编辑都要独立变更理由及历史，需要补充不可变的内容记录；现有审核表不足。 |
| 反馈目标 | 首版 Ticket 已有分析；入口位于 Shadow 区域，面板明确冻结对象 | 若包括 Wiki 某次回答，需按运行绑定并处理运行保留期；不能仅增加按钮。 |
| 原因必填 | 新 Lark 入口必填 | 全局强制时须同步主站及兼容策略。 |

这些待确认项不阻碍设计讨论；实施范围尚未获确认，本次不修改应用代码。

## 功能验收清单（待开发后执行）

前置：准备有权限的 A/B 两个用户，以及未建样本、已有 Eval、已有 Badcase、旧快照样本、无快照、不完整快照各一张 Ticket；准备同 recordId 不同 base/table 的记录、可重跑的 Shadow 输出及 Wiki 历史。使用脱敏或专用测试数据。

| 编号 | 操作 | 通过标准 |
| --- | --- | --- |
| AC01 | 从飞书菜单登录，搜索/深链接选中 Ticket | 原地出现 Badcase 入口；面板 Ticket 与三元组匹配；无选中 Ticket 时不能提交。 |
| AC02 | 无样本时打开后取消 | 样本、原因、审核记录均无新增。 |
| AC03 | 未选标签、原因空白、原因超过 4000 字；再绕过 FE 请求 | 前后端均拒绝新入口的非法输入，显示具体提示，无数据写入。 |
| AC04 | 首次填写合法标签及原因并保存 | 一次提交直接生成 badcase；仅一个样本、一条审核记录；刷新和主站打开后原因一致。 |
| AC05 | 修改已有 Badcase 原因；已有 Eval 转为 Badcase | 更新同一对应样本；未编辑的人工意图和期望结果保持；人/时间更新，标签/原因正确回填。 |
| AC06 | 查看完整/不完整快照及无快照的 Ticket | 沿用快照准入约束；无快照或不满足条件时明确提示，无空样本；完整快照下冻结输出应包括所评的 Shadow 内容。 |
| AC07 | 面板打开后后台更新 thread 或重跑分析，再首次保存 | 拒绝把旧页面反馈写到新输出；重新载入后可对所见输出提交。已有冻结样本则明确显示原输出。 |
| AC08 | 新快照出现，旧快照已有 Badcase | 不把旧样本状态冒充新输出状态；编辑操作绑定明确样本，不改旧快照的冻结内容。 |
| AC09 | 双击、断网后重试；A 保存后 B 保存，再重放 A 的原请求 | 不重复建样本/审核；原请求重试不覆盖 B 的新内容；保存结果以重新读取为准。 |
| AC10 | A/B 同时编辑，包含 Lark 与主站两个入口；或同时首次创建 | 后到的过期表单返回冲突，保留输入并提示重新查看，不静默覆盖；同时创建不虚报双方成功。 |
| AC11 | 无会话、无页面权限、伪造身份、篡改 Ticket/sample 关联 | 按实际访问策略拒绝；标注身份与服务端会话一致。记录级边界必须明确测试，不能以登录成功代替。 |
| AC12 | 保存失败、取消；保存期间切换 Ticket，旧响应迟到 | 失败保留草稿，取消不写入；旧响应不污染新 Ticket，重新进入原 Ticket 可读真实结果。 |
| AC13 | A 创建、B 后续编辑，再分别查看 My evals | 最近标注人为 B，A/B 均保留参与归属；重复保存不膨胀 Ticket 数量。 |
| AC14 | Wiki 页签、人工回复草稿、窄侧栏和移动端 | 不把 Wiki/人工草稿计入本版 Shadow 反馈；面板长文本可滚动、按钮可达、字段和错误可读。 |
| AC15 | 历史空备注样本、原因含 HTML/脚本样式文本 | 旧数据可打开且不补造原因；新入口保存补齐必填原因；原因按文本显示，无脚本执行。 |

若确认逐次变更理由，还需增加“多次修改后原原因、每次理由及操作人时间均可回查”的验收；若确认 Wiki 反馈，还需增加不同运行、相同线程快照下的隔离及历史结果消失后的保留验收。

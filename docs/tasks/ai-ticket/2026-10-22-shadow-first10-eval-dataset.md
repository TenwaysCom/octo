# Shadow AI：Ticket 最初十分钟动作评测数据集

## 目标

建立 50–200 条真实 Ticket 样本，用各 thread 起始十分钟内可见的消息判断回答、追问、需人工处理或等待，支持后续评估与功能实现。区分主问题不清与处理前提不足，覆盖已追问、用户纠正和人工介入。

v2：按同一个Ticket并排查看本次动作候选与原Shadow的意图、诉求描述和问题总结。原分析作为历史参考，不进入前十分钟模型输入或gold；本次不重新调用模型生成原分析。

v3：按会话确认的四分类标准重新逐条检查120例，重点复核human/wait边界；每条展示适用标准、窗口证据、等待是否成立、原/新分类及改判原因。复核仅使用冻结十分钟消息，新版本另存，仍属AI复核而非人工gold。

v4：用户要求将相关改动及eval数据集放入`feat/add-evals`。只提交本次评测脚本、说明、任务及来源能力图、共享索引中的对应条目，以及三个已交付目录内17份冻结数据文件；不混入并行Wiki实现/实验、准备草稿或截图。v4仅创建本地提交；后续远端交付见v5。

v5：用户授权将`feat/add-evals`推送至`origin`。保留远端已有的eval CLI / Shadow v2提交，以普通合并及非强制推送交付；保留工作区全部未提交工作，不创建PR。

- [x] 提供可复查的抽取/校验入口、标注指南、评估指标和人工复核表。

## 背景与范围

依据能力地图 Shadow 缺口。仅做本地只读数据准备与标注，不改 Shadow 运行时、外部工单、数据库或 Wiki，不发模型请求。现有工作区其他 Wiki 与能力地图改动保留。

## 方案与决策

- 用户明确选择“仅凭前十分钟聊天，证据不足就追问或转人工”；不注入Wiki或后台数据，候选回答只限于窗口支持的有限解释/导航。
- 起点取完整导出中第一条消息创建时间作 thread 起点代理，窗口闭区间 `[t0, t0 + 10min]`，判定时点为窗口结束。未额外核对Lark根消息身份。Ticket后补标题/状态、后续消息、既有AI输出不进入输入。
- 缺历史编辑版本和接收时间，不能声称严格历史在线重放；91例有不可读附件、3例源文本已截断，均显式记录。
- 真实样本候选标注由本次 AI 阅读窗口作出；人工审核前不得作为已确认 gold 或评估准确率。
- 初次数据交付在既有gitignored artifacts目录，本机生成权限0700/0600。v4用户明确授权将选定的三个交付目录纳入分支，取代此前“Git仅保存规则、统计、哈希和脚本”的保存边界。数据仍可能含业务信息和姓名，不作为公开匿名数据；Git不保存本机权限作为访问控制。
- 98例开发、22例预留，按thread分组；针对性补选20例全部开发。预留没有回答案例，不能据此评估完整四分类能力。与可索引旧RAG案例交集11例均在开发组，不宣称绝对未见。
- v2只新增比较产物与脚本，沿用v1冻结的120个成员及标注。原导出中111例有Shadow分析段、9例缺失；现有Shadow没有独立question字段，分别展示`intent.summary`（诉求描述）和顶层`summary`（分析总览），不把含解决结果的总结改称十分钟问题真值。
- v3：human表示尚需人工介入且没有明确有效的进行中步骤可等待；wait须有必要且仍有效的待答问题、已承诺的核查/操作或验证任务。仅有转述推荐、请人看看、建议登记bug或先前答复，不能推定已经处理；无待答诉求则单列no_open_request。

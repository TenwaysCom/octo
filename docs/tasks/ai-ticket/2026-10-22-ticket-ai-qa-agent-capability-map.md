# Ticket AI 现有能力盘点与 QA Agent 演进缺口

## 目标

对照仓库梳理 Ticket AI 功能及 QA Agent 演进；以当前已确认的六类模块/入口功能统一列出现有能力、缺失能力、复用依据和建议研发顺序。保留 v3“自动发现新 thread → 创建 Lark Base Ticket → 自动启动 Shadow”入口；用户确认当前由 Support 手工建单。入口可独立或归运行控制与监控，具体归属未定；人工直接处理不建交接模块，运行控制与监控暂缓。本轮仅重整文档，不实施功能或承诺排期；未新增功能要求，需求版本保持 v3。

## 验收标准

- [x] 现有功能按模块列出，并关联代码或任务证据；区分已实现、设计提案与部署验证边界。
- [x] 按 v2 合并问答功能，明确 Shadow、问答、知识库及评测的分工；人工直接处理不建交接模块，运行控制与监控暂缓。
- [x] 补充自动发现/建单/启动 Shadow 的入口及用户确认的手工现状，区分新 thread 发现和已关联 thread 的后续更新。
- [x] 修订目标流程、模块归属选择与阶段边界，移除目标不包含新建 Ticket 的旧表述；保留后台验证及暂缓事项。
- [x] 按统一模块清单逐项列出现有功能与缺口，消除旧实现清单和目标模块划分交叉造成的重复。
- [x] 给出有依赖关系的建议研发顺序、各阶段产出与完成条件；区分当前重点与后续暂缓功能。
- [x] 同步文档与索引，重新核查汇总后的引用、边界与差异。

## 背景与范围

本次为仓库能力盘点和研发建议，不实现新能力、不修改应用配置、不调用真实模型、不向 Lark 发消息。现有工作区包含其他 Wiki RAG 任务的未提交改动，保留原状；盘点以当前工作区为依据，并注明其不等于部署状态。

## 方案与决策

- 产品/架构结论放在 `docs/tenways-octo/`；本任务的进度与验证只记录在此。
- QA 指服务问答与一线支持；自动化测试 Agent 不在本次范围。
- 不把模型自评分、历史完整工单分析或聊天 UI 的连续追问当作在线回复准确率证明。
- v2 取代 v1 中按十类缺口列研发职责的划分建议：RAG/生成/发送归同一问答模块；人工协作/接单/交接系统不在当前范围；运行控制与监控是后续模块，当前不开发。v1 的既有能力证据保留，受影响的边界与路线验收重新打开。
- v3 补充入口自动化需求，取代 v2“未关联 Ticket 的 thread 是否受理尚待确认”的表述：目标包含程序发现新 thread 并创建 Lark Base Ticket、自动开始 Shadow。不是创建 Meegle 工作项，也不意味着启动自动回复；去重、已有人工工单关联及失败恢复列为设计边界。模块独立与否、发现范围/方式、实施顺序留待设计，本次不新增实现任务或外部写入。

# 受限阈值兜底采用（v16）

用户于2026-10-22明确要求采用该策略。需求与最终状态以[任务记录](../2026-10-21-wiki-rag-vendor-bill-diagnosis.md)为准；这是规则接入及回归，不是新一轮模型实验，也不改写v10未通过的历史结论。

## 实际行为

1. 仅专用rerank模式、正常阈值0.7且没有任何返回分数达到0.7时，才尝试兜底。显式其他最小分数配置和general模式沿用原行为。
2. 只考虑原始全体返回分数的第一名，要求明确为Support Wiki、分数≥0.3、领先原第二名≥0.2。分数与差值都含等号；差值比较只容忍机器表示的舍入误差。
3. 第二名缺失时不假定其为0；Ontology仍参加原分差计算。Top1是Ontology不跳过它找Support Wiki；分数／索引异常和请求失败不兜底。
4. 必须由原有selectEvidence取得非空完整原文，所有实际返回单元complete为true、合计≤2400字符，且来源限定后的Wiki正文非空。预览摘录、不完整快照、空正文、缺原文或超预算均不能兜底；必要前提和后续纠正仍按原reader完整保留。
5. 最多一篇，保留草稿／未知／未解决与环境边界，强制历史参考、处理前提未核验，并附明确的低分兜底限制。没有第二次模型调用、预算扩张、来源补搜或G。
6. 只在分数通道为空时触发；高分文章后来证据不足不激活兜底，低Top1后来失败也不转选第二名。触发状态保存在单次retrieve调用中，避免并发串扰。

## 实际验证

- 238项相关单元／mock、服务端TypeScript build通过，其中新增28项兜底验证。
- 覆盖0.3／0.2含等号、低于下限／小分差／同分、缺第二名、无召回／无分数、Ontology首位及竞争者、单篇上限、来源不完整／缺失／超预算、正常0.7通道与自定义阈值、并发状态、异常不回原候选。
- 真实filesystem reader＋mock精排集成：完整保留后续否定；完整上下文超2400则整组拒绝，不裁掉纠正来过门槛。mock验证没有生成真实模型答案。
- v15已采用的字段召回及共用Wiki文字未变；v5～v15旧冻结证据未改写。本次应用仅新增service策略与对应测试，没有安装实验策略A／B／C／D或引入新依赖／配置项。

具体结果和完整差异见[验证记录](verification.json)与[应用补丁](applied.patch)。原文完整性要求比v10仅检查非空更明确，因此不直接复用其旧四题补回数；召回字段与正文输入也已在v15变化，旧分数不用于证明当前组合质量。

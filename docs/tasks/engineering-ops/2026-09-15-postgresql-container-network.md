## v3 代码审查结论

1. **空结果没有反馈到调度频率。** `worker.py:4828` 丢弃 `run_once()` 的布尔返回值；`worker.py:4837` 每轮补满全部空槽，`worker.py:4841` 固定等待默认 1 秒。无任务时仍持续发起同样的查询。可以保留并发容量，为空结果增加有上限的退避和任务唤醒机制。
2. **同通道多个槽位重复扫描同一组任务类型。** `worker.py:1769` 每次先逐 kind 回收超时任务；`worker.py:2105` 又逐 kind 尝试领取。默认通道为 heavy 2×3、download 2×1、delete 2×3、service 4×6，因此每个空闲全轮执行 38 次回收和 38 次领取，另有 2 次历史锁清理、10 次 drain 检查。可将回收独立为受控周期检查，并合并同通道空队列探测；保留 kind 特定恢复、原子领取和锁规则。
3. **连接池常驻容量低于同步轮询峰值。** `engine.py:19` 只保留 5 条，而执行器同步补满 10 槽；超过常驻容量的连接在归还队列满时关闭。实际内存实验验证该机制，是既有短连接现象的合理来源。先抑制同步空轮询，再结合 HTTP、通知、调度器共享 operations engine 的需求评估容量，不直接全局扩池。

### 必须保留的行为与审查边界

- `FOR UPDATE SKIP LOCKED`、owner token、资源锁基数校验、drain 原子保护和按类型恢复是已有正确性契约，见 ADR-0050 与 operation-state-machine；不因性能问题直接删除。
- `OperationUnitOfWork.__exit__` 回滚未提交事务、归还连接是正常清理；不能把这些 `ROLLBACK` 计为 SQL 报错，也不能把 `.close()` 全部理解为关闭物理连接。
- 已有并发测试覆盖删除通道不会被长任务占满；本次检查的测试未覆盖空闲查询预算和退避。没有应用代码修改，因此未运行完整套件或新生产采样。

## v4 磁盘写入判断

- 四类任务 SQL 的 UPDATE 都受 candidate 结果与 operation_id 关联约束；没有候选任务时不会批量更新目标行。任务出现时，领取会更新任务/锁，超时回收会更新步骤/任务/锁，历史清理会更新目标锁和任务，并由业务层记录事件/审计。
- 不能将空轮询等同零磁盘写入：`runtime_drain.py:39` 使用 `FOR SHARE` 锁定实际存在的 profile 行；PostgreSQL 行锁可能修改页面并产生 WAL，即使最终事务回滚。参考 [PostgreSQL 17 行锁说明](https://www.postgresql.org/docs/17/explicit-locking.html)。统计口径参考 [累计统计系统](https://www.postgresql.org/docs/17/monitoring-stats.html)。
- 本次目标表无增删改、读取缓存命中，实例 WAL 1.36–4.40 KiB/s、容器块写入 14.13–17.60 KiB/s；当前证据不支持这些空轮询造成很大的磁盘写入压力。其更明显成本仍是重复请求、SQL 处理和事务/连接周转。
- 无 checkpoint 发生的 60 秒采样不能代表后续刷盘峰值；其他数据库/表写入也包含于实例与容器统计。未改业务代码、监控配置、触发器或日志设置。

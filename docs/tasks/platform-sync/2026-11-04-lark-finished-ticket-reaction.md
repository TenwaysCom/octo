# Lark 工单按配置状态自动添加 Done 表情

## 目标

使用 Application Bot 定期查询目标 Lark Base/Table 中最近修改且当前状态匹配配置值的工单，给工单消息链接指向的话题根消息添加 `DONE` 表情。目标状态默认 `Finish`，可以通过配置修改。v6 按用户要求先完成无变化跳过写入，实施时不启用任务或执行真实批量测试。v7 修复已启用任务的同日窗口漏选，为指定工单 2464 补标，并让既有 Worker 加载修复。

## 验收标准

- [x] 明确处理范围为目标 Base/Table 所有工单关联的话题，不限制来源群。
- [x] 明确首次启用不补历史，以及扫描、去重、权限失败和结果未知的处理方案。
- [x] 明确目标状态可配置，默认 `Finish`，扫描筛选与添加表情前的状态复核共用同一生效配置。
- [x] 明确每 10 分钟扫描一次，增量起点从上次成功扫描水位回退 5 分钟，并受首次启用边界约束。
- [x] 实现独立 Worker 任务，持久化启用边界、扫描进度和单条处理结果。
- [x] 本地验证 10 分钟调度及 5 分钟重叠窗口、默认及自定义目标状态、配置变更后的待办复核、首次启用、重叠分页、进程重启、重复消息链接、权限不足和写入超时等场景。
- [x] 提供区间只读预览及单条显式执行入口；Bot 表情归属及重复执行在本地模拟验证，真实工单验证待用户提供，批量测试由用户执行。
- [x] 数据同步页从“尚未实现”升级为真实配置与运行记录展示。
- [x] v7：移除日内窗口的远端 TODATE 上界，服务端按系统更新时间精确执行半开时间窗；回归覆盖真实日精度行为、同日和跨日边界及宽筛多页结果。
- [x] v7：相关测试和构建通过，真实只读预览能重新发现 2464；用既有单条入口补 DONE，读回当前应用归属，并验证重复执行不重发。不回退自动水位，不触发历史批量补标。
- [x] v7：既有生产 Worker 等待在途任务完成后加载修复，启用边界保持不变，首轮自动扫描成功。

## 方案与决策

v7：用户授权修复运行时漏选。仅调整 Done 服务的远端筛选组合，保留现有本地精确范围判断、入队/水位和未知写入保护；复用既有单条入口补标指定 2464。生产 Worker 已在运行旧代码，核对其 PID、启动路径及自动重启后，通过现有 SIGTERM 处理等待在途任务自然完成并由 PM2 自动重启加载修复，避免重启命令的强制超时。不修改共享增量同步方法、不新增表/配置、不回退扫描进度、不对其他遗漏记录做批量写入。

### Worker 和身份

在现有 platform worker 内增加独立任务 `larkTicketDoneReaction`，默认关闭、每 10 分钟执行，回退窗口默认 5 分钟。任务引用全部既有 Base/Table 配置及状态、最后修改时间字段，不增加来源群白名单，也不依赖工单是否由自动登记功能创建。

读取 Base、解析消息及查询/添加表情统一使用既有 `LARK_APP_ID` / `LARK_APP_SECRET` 构造的应用客户端，沿用 SDK tenant token 缓存与过期获取机制；不回退个人用户权限。复用 coordinator 的互斥租约与 actionRunId 追踪，每个目标维护独立进度。

### 目标状态配置

`scheduler.tasks.larkTicketDoneReaction` 包含 `enabled`、`intervalMinutes=10`、`overlapMinutes=5`、`targetStatus="Finish"`。状态值为 Base 实际选项名称，校验去除首尾空白后非空并精确匹配。状态字段名继续引用既有 Base/Table 配置的 `statusFieldName`，区分字段名称与状态值。修改配置后需重启 Worker，待办执行前按新配置重新复核。

源端发现与单条执行前复核使用同一生效配置；配置变更后，已入队但尚未执行的记录也按新的目标状态复核。修改状态配置不重置启用边界或水位，不触发历史补扫；已添加的表情按本期仅添加的范围保留。

### 增量发现

1. 第一次启用时持久化 `enabledAt` 和初始扫描水位，不扫描此前数据。重启或再次启用沿用原进度，不重新初始化启用边界。
2. 每轮固定扫描截止时间为本轮开始时间，按 Base 的最后修改时间筛选，起点为 `max(enabledAt, watermark - 5 分钟)`，使用半开时间区间。`watermark` 是上次成功扫描的截止时间。重叠窗口用于容忍边界和短暂可见性延迟，不能越过启用边界。正常每 10 分钟执行时，每轮覆盖约 15 分钟；停机或扫描失败后继续从旧水位回退，覆盖尚未成功扫描的增量。
3. 在源端以 `TODATE(start)` 下界及当前状态严格匹配 `targetStatus`（默认 `Finish`）宽筛，不使用会截断同日窗口的 `TODATE(end)` 上界。分页读取全部候选，按系统 `record.updated_time` 毫秒值精确判断 `[start,end)` 后持久化单条待办，目前不设固定条数上限；全部分页及待办落库成功后才推进本轮水位。发现失败保留旧水位；已入队项靠幂等约束合并。
4. 修改时间字段应覆盖全部相关业务字段，响应缺失可信源更新时间或筛选配置错误时明确失败，不用本地同步时间替代。
5. 单条发送前重新读取源记录，复核当前状态仍匹配生效配置的 `targetStatus` 且消息链接未变化；变化时取消旧候选，后续发现处理新状态。读后再次修改仍存在跨平台竞态，不宣称原子状态同步。

这里“新的”指启用后有修改且当前状态匹配 `targetStatus` 的记录。以默认 `Finish` 为例：很早创建、刚完成的工单会被发现；历史已完成且未再修改的记录不会补扫。历史已完成记录在启用后编辑其他字段，也可能进入候选。本方案不保证捕获两次轮询之间短暂出现后又被改走的目标状态，也不承诺只识别状态字段的真实流转事件。

现有 `bulkSyncLarkBaseTickets()` 会过滤终态，不能作为完成工单发现入口。直接复用 Lark adapter 的分页读取能力，建立专门的完成筛选，不依赖 Octo 本地快照先同步成功。

### 解析关联话题

优先使用链接中明确的根 `messageid`，读取消息并验证话题归属。兼容既有 Open ID 链接及客户端数字 thread ID；数字 thread ID 与 Open API 的 `omt_` 标识不同，必须通过已有可信映射或话题回复解析真实根 `om_` 消息 ID。

缺少链接、链接无效、找不到根消息、根消息已撤回、或 Bot 无权读取时记录单条原因，不猜测 message ID。数字话题没有回复且链接没有根消息 ID 时，保留待人工补充信息的结果。不同群分别按应用实际权限处理，不扩展应用授权。

### 幂等与结果确认

以应用身份、根消息 ID 和 `DONE` 作为表情幂等范围，并保留 Base/Table/Record 与源更新时间供追踪。多条工单关联同一消息时合并表情操作。

添加前分页检查该消息的 `DONE` 表情；仅当前应用的表情算完成，其他用户的同款表情不能代替 Bot 的结果。成功后保存 reaction ID，并通过读回确认操作人是当前应用。adapter 新增分页查询与返回 reaction 对象的创建方法；既有 `addMessageReaction()` 保持 void 契约，供登记流程继续复用。

超时或连接中断时先标记结果未知，下一次只读对账；确认本应用的 `DONE` 已存在则完成。不能确认写入失败时不盲目重发。明确拒绝、限流等可按错误分类退避重试；权限缺失、消息不存在等保留可诊断状态，不阻断其他工单，也不无限重试。

PostgreSQL 的 `lark_ticket_done_scans` 保存启用边界及水位，`lark_ticket_done_reactions` 按应用、记录、源版本和消息链接保存不可变待办，以及根消息、阶段、attempts、next_retry_at、reaction_id、error_code、action_run_id。正常生命周期 pending → adding → done；源状态/链接改变为 cancelled，明确权限/输入问题为 blocked，未知写入为 outcome_unknown。全部入队后才推进水位，部分入队失败仍由旧水位重新发现并去重。

目标表 scope 和应用/根消息 scope 分别使用 coordinator 租约，前者保护扫描、后者串行化同一表情效果。锁内还查询同一应用/根消息的所有未知操作，防止新版本或另一条关联记录绕过旧结果未知而重新派发。单条最多五次自动失败尝试，显式单条入口可继续人工触发读取；未知写入始终只能读回核实，不能重发。单条错误不阻断后续工单，本轮存在处理失败时将目标任务记为失败，日志只记录安全标识及错误码。

### 验证入口

`pnpm --dir server platform:lark-ticket-done` 提供不改变自动水位的区间只读预览及单条 record 执行，两者与 Worker 复用同一服务。必须指定已配置 Base/Table；单条只有显式 `--apply` 才写入，区间不接受 apply。预览不建待办、不迁移表或推进水位；单条 CLI apply 只初始化 Done 两张表及索引，不触发全应用迁移，也不改变自动游标。v6 未执行真实写入；v7 使用同一 runtime 的单条方法补标已定位的 2464，无需再次执行 DDL，真实结果记录如下。真实批量测试仍不在本次范围。

### 2026-11-04 最新 Finish 漏标的运行时诊断

诊断阶段仅定位原因，所有平台调用均为读取；数据库使用 `BEGIN READ ONLY`，没有创建待办、补表情、改水位、修改配置或重启进程。以下为修复前证据，v7 的实际写入和加载结果另列于后。

- 当前本地配置的 scheduler 与 Done 开关均为 true，间隔 10 分钟、重叠 5 分钟、目标 `Finish`。实际任务 17:45、17:55、18:05 均为 succeeded；18:05:12 的扫描截止水位已持久化，但 Done 待办表为空。
- 真实 Base 最新 Finish 为编号 **2464** / record `reczz28VWqVoYhsb`，系统最后修改时间 `2026-11-04T09:48:00.000Z`（北京时间 17:48）。配置字段“最后更新时间”为 type 1002，值 `1793785680000`，与系统时间一致，不是时间字段没有追踪状态。源消息根 ID `om_x100b61999ef1b4b8fe1f49dfa4bdbdb`，应用自己的 DONE 和任何 DONE 均不存在，且没有该 record 的表情待办。
- 已执行的只读复现 `node /tmp/octo-check-latest-done.mjs` 以缺少本应用 DONE 返回 exit 2；actionRunId `605779ea-90d1-4022-b0f9-89fb7bcbeebc`。脚本只输出状态、时间、编号和结果标识，临时脚本在诊断结束清理；以下表达式及结果保留为重现依据。

对该同一张表、同一应用身份，以 UTC `[2026-11-04T09:40:00.000Z, 2026-11-04T09:55:00.000Z)`（北京时间 17:40–17:55）对比，status 条件始终为 `CurrentValue.[状态] = "Finish"`：

| 只读查询条件 | 平台返回数 | 包含 2464 | 返回记录再经系统时间精确过滤 |
| --- | --- | --- | --- |
| `>= TODATE(start)` 且 `< TODATE(end)`，当前实现原表达式 | 0 | 否 | 0 |
| 重新以普通双引号组装相同上下界 | 0 | 否 | 0，排除引号转义问题 |
| 仅 `>= TODATE(start)` | 7 | 是 | 1，即 2464 |
| `>= TODATE(start)` 且 `< TODATE("2026-11-05T00:00:00.000Z")` | 7 | 是 | 1 |
| 直接用 Unix 毫秒数字作日期字段的上下界 | 0 | 否 | 0，不能假设数值表达式可直接代替日期表达式 |

首轮条件对比追踪 ID 为 `c4220c62-21ed-42b2-8b33-c2f7e8437103`，补充边界对比为 `5ebd2c6d-3128-41ea-843d-7060f7e4ce4a`。宽筛返回记录包含 UTC 02:31、06:12、06:23、07:11、07:12 与 09:48，证明这套 `TODATE` 条件不能表示所需的日内分钟精度；次日上界可以包含目标，当前同日上界将其排除。官方 [Base 函数大全](https://www.larksuite.com/hc/zh-CN/articles/914838661184-多维表格公式函数大全)将 TODATE 定义为文本转日期；本结论的具体日内过滤行为来自上述真实 API 对比。

根因位于 `lark-ticket-done-reaction.service.ts` 的 discover：将两个带时分的 ISO 字符串分别放进 `TODATE` 构造远端上下界，同日窗口因此返回空；服务随后按“完整分页成功、无候选”推进水位，形成静默漏选，未进入表情权限或 POST 阶段。新编译服务的同条件读取也可复现，因此不依赖猜测常驻版本。当前水位已越过 17:48，单纯修复未来扫描仍不能保证自动找回该条。

诊断阶段验证的最小修复方向：远端状态条件及日期下界仅做宽筛，删除会截断日内范围的远端上界；继续使用现有 `record.updated_time` 的毫秒值在服务端严格执行 `[start,end)`，并在入队全部成功后推进水位。补齐能模拟远端日精度的回归后，再明确恢复启用边界内被遗漏的范围或指定单条；不得无条件回退水位或全量补历史。该阶段未实施修复或触发真实补标，后续由 v7 完成。

| 样本 | 已收录工单 | 输入证据项 | 材料复核结论 |

| 用户 A | 8 | 16（字段8、Shadow8） | 可形成车辆模块、权限/区域可用性、记录维护、差旅流程等历史服务场景；来源包含 stale 记录和部分缺失日期，不能宣称是当前职责/当前状态。 |

私有输入材料在 `/tmp/octo-profile-validation-n05Ard`，每个文件权限0600，目录由 mkdtemp 创建。仓库不保存真实人员标识、私有来源映射或聊天正文；临时目录不是长期证据存档，也没有自动清理任务。

## 应提炼的内容及应留空的内容

以下是旧需求下的人工材料复核结论，不是已运行模型的输出，也不是新需求三类特点的验收结果：

- 用户 A：服务上下文可概括为记录中涉及车辆模块及相关流程；历史方案按适用场景分别保留，例如记录维护指引与区域模块可用性解释。Shadow 中的“已解释/已建议”不能升级为“用户实际执行并确认有效”。新加入差旅工单时，扩充服务上下文，不能推断岗位变化。
- 用户 B：仅输出有限的报错处理背景及证据缺口。新增第二张澄清工单后，应增加“上下文不足/可能为同一事件追问”的限制，而不是生成“经常遗漏信息”标签。
- 两位用户：本轮没有提供角色已确认的需求人原始消息，support_preference、communication_pattern 应为空。Shadow 中的人称和匿名角色不足以完成归属验证。

## 待授权后执行

新需求需先补充并核对两用户的原始消息角色。现有脚本已切换v3结构，但只有需求字段/Shadow，适合部分验证及性格/沟通缺证据降级；完整验证入口需补证后继续。模型外发仍需授权，前次审批拒绝不因格式变更而解除。

从 server 目录运行 `node dist/scripts/validate-user-profile-extractor.js --model`。使用已配置 `zcode / glm-5.3-flash`，两用户各执行首次与加入留出工单后的重新归纳（A为7→8、B为1→2），再验证相同输入不发起第三次调用。更新为样本重放，不写真实工单。

新审核点：仅输出三类特征；性格表述是有原始证据的场景化行为倾向而非固定标签；需求总结描述关注点和诉求模式而非模块清单；B不把关联追问当重复事件；两用户不从 Shadow 单独生成性格/沟通特点；不输出服务概况、实时状态、行动建议或回复草稿；源缺口与反例必须保留。记录模型实际返回结果并逐条审核后才能勾选任务的双用户提炼验收。
